## 1. 開発環境とAIモデルの使い分け戦略 (Gemini 3.8 Flash vs Gemini 4 Argon)

Antigravity 等のエージェント型AI開発環境における、タスク性質に応じたモデル最適化戦略。

### 1.1 モデル特性と適材適所の判断基準

| 開発フェーズ・課題                       | 推奨モデル           | 選定理由・役割                                                                                    |
| :--------------------------------------- | :------------------- | :------------------------------------------------------------------------------------------------ |
| **GUI境界設計・非同期アーキテクチャ**    | **Gemini 4 Argon**   | UIスレッドとワーカースレッド間のチャネル設計、ライフサイクル整合性の維持。                        |
| **Rust 借用・ライフタイムの難解エラー**  | **Gemini 4 Argon**   | 即時モード（`eframe::App::update`）内での可変参照競合やスレッド境界制約（`Send + 'Sync`）の解消。 |
| **マルチクレート境界の整理**             | **Gemini 4 Argon**   | `vivivi-core`、`vivivi-vi`、`vivivi-modes`、`vivivi-app`、`vivivi-gui` 間の依存関係再定義。       |
| **ウィジェット配置・レイアウト調整**     | **Gemini 3.8 Flash** | 低レイテンシを活かした試行錯誤、手数の多いコード生成。                                            |
| **局所的な構文エラー・リファクタリング** | **Gemini 3.8 Flash** | 開発テンポを落とさず高速に消化するタスク群。                                                      |

### 1.2 実務的な切り替え運用ルール
1. **通常の実装は 3.8 Flash で回す**: 基本的なコーディング、ウィジェット追加、スタイル微調整。
2. **「2往復ルール」で 4 Argon へスイッチ**: 3.8 Flash に修正を指示して2往復してもコンパイルエラーが通らない（別の借用エラーを生む）場合は、即座に 4 Argon に切り替え、`cargo check` のログを丸ごと渡して根本設計から見直させる。
3. **骨格が通ったら 3.8 Flash に戻す**: アーキテクチャの芯が通った段階で再び Flash に戻し、実装スピードを最大化する。

## 2. GUI基盤の役割分担：eframe と egui の違い

### 2.1 役割の明確な分離

* **egui (GUIライブラリ)**:
  * 純粋なUIロジック、レイアウト計算、入力イベント判定、描画メッシュ生成を担当。
  * OSへの依存を持たず、これ単体ではウィンドウを表示できない（純粋な描画命令生成器）。
* **eframe (egui framework / 公式フレームワーク)**:
  * OSウィンドウの管理（winit等）、GPU描画バックエンドの初期化（wgpu / OpenGL）、OS入力イベントの抽象化。
  * `eframe::App` トレイトを提供し、`update` 関数を毎フレーム呼び出すイベントループ基盤。

### 2.2 構造関係図

```text
+-------------------------------------------------------------------+
| OS (Windows / macOS / Linux / WebAssembly)                        |
+-------------------------------------------------------------------+
                                ▲
                                │ ウィンドウ管理 / 入力 / GPU
+-------------------------------▼-----------------------------------+
| eframe (NativeOptions, run_native, イベントループ)                 |
+-------------------------------------------------------------------+
                                │ 毎フレームのコンテキスト提供 (ctx)
+-------------------------------▼-----------------------------------+
| egui (CentralPanel, Layout, Painter, Visuals, 状態判定)           |
+-------------------------------------------------------------------+
                                ▲
                                │ 呼び出し
+-------------------------------▼-----------------------------------+
| vivivi-core / vivivi-modes (GapBuffer, Undo, 罫線/CSVロジック等)  |
+-------------------------------------------------------------------+
```

## 3. RustネイティブGUIフレームワークの比較検討

Webフロントエンド技術（React, HTML/CSS, Tauri等のWebView）を除外した、ピュアネイティブ描画スタックの比較検討。

| フレームワーク                | 描画アーキテクチャ                                   | 実行速度・描画性能                               | 特徴・デザイン性                                                            | AI (LLM) 支援精度                    | 今回の適性                           |
| :---------------------------- | :--------------------------------------------------- | :----------------------------------------------- | :-------------------------------------------------------------------------- | :----------------------------------- | :----------------------------------- |
| **egui + eframe**<br>*(採用)* | **即時モード (Immediate)**<br>毎フレーム全体を再評価 | **極めて高速**<br>(軽量GPU直結)                  | 単一のRustコードで完結。テーマ（Visuals）を上書きすることでモダン化が可能。 | **極めて高い**<br>(作例・知見が豊富) | **最適**<br>(TUIロジックと直結)      |
| **GPUI**<br>*(Zed基盤)*       | **リテインド＋GPU直結**<br>(React/Tailwind寄り)      | **最速・極限の低遅延**<br>(Metal/DirectX/Vulkan) | Tailwind CSS風のユーティリティ記法。汎用部品が乏しく自作前提。              | **低い**<br>(API変更多、知見少)      | **時期尚早**<br>(実装・設計コスト大) |
| **Slint**                     | **リテインド型**<br>(宣言的DSL + Rust)               | **最速クラス**<br>(MCUでも動作)                  | 専用言語（`.slint`）を使用。QtのQMLに近く、標準で整ったUI。                 | **高い**<br>(構文が明確)             | **保留**<br>(DSL習得と同期層が必要)  |
| **Iced**                      | **リテインド・リアクティブ**<br>(Elm Architecture)   | **高速**<br>(wgpuベース)                         | Model-Update-Viewの強固な状態管理。コード量は増えるが堅牢。                 | **普通〜高**                         | **保留**<br>(キー即時性との相性)     |

## 4. なぜ Zed は GPUI を自作・採用したのか

Atom の開発者（Nathan Sobo ら）が立ち上げた Zed が、既存フレームワークを使わずに GPUI を開発した背景：

1. **Atom（Electron / Web技術）の限界の打破**:
   DOM、CSSエンジン、JavaScriptランタイムを挟む限り、タイピング遅延（Input Latency）をゼロにすることは構造上不可能であるという結論。
2. **ProMotion (120Hz) の完全追従**:
   1フレームあたり 8.33ms 以内に全描画を完了させるため、汎用GPU抽象化を排してプラットフォーム低レベルAPI（macOSのMetalなど）に直結させた。
3. **即時モード（egui等）のバッテリー・CPU限界**:
   巨大ファイルを高速スクロールする際、毎フレーム数万行のレイアウト計算をCPUで愚直に回す方式を避け、差分更新とGPUネイティブキャッシュを徹底。
4. **マルチスレッド非同期アーキテクチャ**:
   Tree-sitter（構文解析）、LSP（Language Server）、非同期I/Oが走っても、UIスレッドが絶対に1フレームもブロックされない機構をフレームワークの核に据えた。

## 5. egui のデザイン改善と脱「野暮ったさ」の手法

egui が野暮ったく見える主因は「ゲーム開発・デバッグ用ツールのデフォルト設定」にある。全体テーマ（`Visuals`）を起動時に上書きすることで、洗練されたモダンエディタの外観が得られる。

### 5.1 代表的なモダンテーマの比較

| 項目                 | **Tokyo Night**                            | **Catppuccin (Mocha)**                         |
| :------------------- | :----------------------------------------- | :--------------------------------------------- |
| **ベーストーン**     | クール・深海のような青紫・ネイビー         | ウォーム・モカ／エスプレッソ調のダークグレー   |
| **アクセントカラー** | ネオンシアン、ライトブルー、マゼンタ       | ラベンダー、ミント、ピーチ、ローズウォーター   |
| **UIの印象**         | サイバー感、引き締まったシャープなテック感 | 柔らかく目に優しい、居心地の良い佇まい         |
| **向いている用途**   | ログビューア、ターミナル連携、モニタリング | テキストエディタ、ドキュメント閲覧、常駐ツール |

### 5.2 デザイン手戻りを最小化する 4 原則
1. **境界線（Stroke）を消す**: 標準の白枠で囲まれた四角いボタンをやめ、ホバー時の明淡差で表現する。
2. **角丸（Rounding）の付与**: ボタンやパネルに 4px〜6px の丸みを持たせる。
3. **背景の3段階コントラスト**:
   - ベース背景（一番暗いエディタ領域）
   - パネル／サイドバー（中間の暗さ）
   - 選択要素・アクティブ行（少し明るい）
4. **等幅フォントと線画アイコン（Phosphor Icons等）の活用**:
   テキストだけのボタンを避け、適度な余白（`item_spacing`）を確保する。

## 6. GUIフォント戦略：PlemolJP の標準採用と「半角1:全角2」の死守

TUI版は実行環境であるターミナル（Windows Terminal, Alacritty, WezTerm等）の設定フォントに委ねられますが、**GUI版（`vivivi-gui`）では公式標準フォントとして『PlemolJP』を採用** します。

### 6.1 PlemolJP を標準採用する決定打

1. **Zed と同じ美しさ（IBM Plex Mono 由来）**:
   Zed のエディタフォント（`Zed Mono`）のベースである **「IBM Plex Mono」** を欧文グリフに使用しているため、Zed と同等の洗練された知的かつモダンなコーディング体験が得られる。
2. **完全な「半角 1 : 全角 2」の等幅比率（East Asian Width）**:
   日本語グリフ「IBM Plex Sans JP」と精密に合成されており、全角文字の幅が半角文字の完全に2倍となるよう設計されている。
   - **罫線モード（Box Drawing）**: 縦横の交差点（`┌ ─ ┐ │ ┼`）が1pxもズレず直交する。
   - **CSVモード & Markdownテーブル**: カラム区切りが綺麗に垂直整列し、ガタつきを根絶できる。
3. **安全なライセンス（SIL Open Font License）**:
   商用・個人利用問わず自由に使用・再配布可能であり、将来的なポータブル配布時のアプリ同梱にも適している。

### 6.2 フォント読み込み・フォールバック階層設計

```text
[第1優先: 公式推奨]
PlemolJP / PlemolJP Console（アプリ同梱またはシステムインストール済み）
       │ (見つからない場合)
       ▼
[第2優先: Windows標準高品位]
BIZ UDゴシック (MORISAWA) / MS Gothic
       │ (非Windows / 見つからない場合)
       ▼
[第3優先: システム標準]
OSデフォルト等幅フォント (Monospace / Courier)
```

## 7. プロジェクト構造：マルチクレート構成の意義

vivivi プロジェクトがマルチクレート（Cargo Workspace）構成を採用している本質的理由：

1. **ロジックの完全分離**:
   テキストエディタの本質（`GapBuffer`, `UndoMgr`, Viモードエンジン、罫線・CSVロジック）を独立クレートに閉じ込め、TUI と GUI で 100% 共有。
2. **不要な依存関係の肥大化防止**:
   `vivivi-app`（crossterm/ratatui による TUI）と 将来の `vivivi-gui`（wgpu/eframe による GUI）の巨大な依存が混ざり合わないよう物理隔離。
3. **差分コンパイル時間の極小化**:
   GUIの見た目やレイアウトをどれだけ書き換えても、重い `vivivi-core` や TUI実装の再ビルドは一切走らない。

```text
vivivi/
├── Cargo.toml               (ワークスペース定義)
├── crates/
│   ├── vivivi-core          (ヘッドレスな純粋バッファ・Undo層)
│   ├── vivivi-vi            (Viモード・キーバインド・Exコマンド解析)
│   ├── vivivi-modes         (罫線、CSV、Migemo、アウトライン、差分等の独自機能)
│   ├── vivivi-app           (現在稼働中の Ratatui TUIフロントエンド)
│   └── vivivi-gui           (Phase 5 で新設予定の egui / eframe フロントエンド)
```

## 8. ViVi / openViVi の歴史と ViViVi の存在意義

### 8.1 作者・津田伸秀（つだ のぶひで）氏の足跡
* **Windows黎明期の金字塔**:
  Windows 95/NT 時代に Win32 API を直接叩くネイティブな Vi クローンとして ViVi を開発・公開。卓越した安定性と速度で絶大な支持を得た。
* **日本語（IME）と Vi の完全調和**:
  当時の海外製エディタが太刀打ちできなかった「日本語インライン入力」と「Viのモード遷移」のシームレスな統合を実現。
* **Qtへの移植とオープンソース化**:
  クロスプラットフォーム対応を目指し、膨大な C++ コードをご自身で Qt に移植して **openViVi** として公開。

### 8.2 Zed が存在しても「ViViVi」が必要な理由
Zed は「フルスペックのコード開発環境（IDE）」であり、重機の立ち位置にある。対して ViViVi は「超軽量で独自の切れ味を持つ職人ツール」として確固たる住み分けが存在する。

1. **罫線モード（Box Drawing）**:
   カーソルを矢印で動かした軌跡に自動で罫線（`┌ ─ ┐ │ └ ┘ ┼`）を引き、交差点を自動判定する。メモ書きや仕様書のテキスト図解を 0 秒で作成可能。
2. **CSV モード（カラム整形・編集）**:
   表計算ソフトを起動せずとも、縦列を整列表示し、Vi のキー操作でカラム間を自在に飛び回って編集・ソート・抽出を行う。
3. **TUI と GUI のハイブリッド**:
   SSH接続先やターミナル内では `vivivi`（TUI）、デスクトップでは `vivivi-gui` という、同一の操作体系とコアロジックを環境に応じて使い分けられる。

## 9. GUI（egui）実装に向けた具体的な指示プロンプト手順

Phase 5 実装着手時にそのまま利用できるプロンプト雛形：

### ステップ 1: スタイルとフォント初期化（PlemolJP 優先設定）
```text
egui / eframe を用いたViライクなテキストエディタのGUIクレート（vivivi-gui）を新設します。
Tokyo Night（またはCatppuccin Mocha）を基調としたモダンなエディタ外観に設定します。

以下の初期化コードを作成してください：
1. cc.egui_ctx.set_visuals:
   - 背景は完全な黒を避け、エディタ背景、パネル背景、ステータスラインで3段階の明淡をつける
   - ボタン等の余計な枠線（Stroke）を排除し、角丸は 4px とする
2. cc.egui_ctx.set_fonts (PlemolJP 最優先のフォント定義):
   - egui::FontDefinitions を構成
   - "PlemolJP"（または "PlemolJP Console"）のTTF/OTFデータをフォント定義に登録
   - FontFamily::Monospace および FontFamily::Proportional のファミリーリスト先頭に "PlemolJP" を追加
   - フォールバックとして "BIZ UDゴシック"、システムの等幅フォントを後続に設定
```


### ステップ 2: 画面骨格（レイアウト）
```text
eframe::App の update 内でエディタ画面の基本レイアウトを構築してください。
中身のロジックはモックで構わないので、コンテナ分割のみを正確に実装してください：
1. TopBottomPanel::top("menu_bar"): コンパクトなメニューバー
2. TopBottomPanel::bottom("status_bar"): モード表示（-- NORMAL --）、カーソル位置、最下段コマンドライン
3. CentralPanel: テキスト編集領域（行番号 + テキスト描画）
リサイズに追従してエディタ領域が最大化するようにしてください。
```

### ステップ 3: キー入力横取りと描画結合（最重要）
```text
既存の vivivi-core / vivivi-vi クレートをGUIに接続します。
※重要：egui標準の TextEdit ウィジェットは使用しません。

要件：
1. CentralPanel 上で ctx.input(|i| ...) を使い、Rawキーイベント（Esc, h, j, k, l, i, コロン等）を拾って vivivi-vi の入力ハンドラへ流し込む
2. CentralPanel::show 内で ui.painter() を使い、行番号とテキスト本文を等幅フォントで整列描画する
3. 現在のモードに応じたカーソル（ブロック／Iビーム）を描画する
```
