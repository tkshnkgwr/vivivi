## 1. 開発環境とAIモデルの使い分け戦略 (Gemini Flash vs Gemini Pro / Argon)

Antigravity 等のエージェント型AI開発環境における、タスク性質に応じたモデル最適化戦略。

### 1.1 モデル特性と適材適所の判断基準

| 開発フェーズ・課題                       | 推奨モデル               | 選定理由・役割                                                                                    |
| :--------------------------------------- | :----------------------- | :------------------------------------------------------------------------------------------------ |
| **GUI境界設計・非同期アーキテクチャ**    | **Gemini Pro / 4 Argon** | UIスレッドとワーカースレッド間のチャネル設計、ライフサイクル整合性の維持。                        |
| **Rust 借用・ライフタイムの難解エラー**  | **Gemini Pro / 4 Argon** | 即時モード（`eframe::App::update`）内での可変参照競合やスレッド境界制約（`Send + 'Sync`）の解消。 |
| **マルチクレート境界の整理**             | **Gemini Pro / 4 Argon** | `vivivi-core`、`vivivi-vi`、`vivivi-modes`、`vivivi-app`、`vivivi-gui` 間の依存関係再定義。       |
| **ウィジェット配置・レイアウト調整**     | **Gemini 3.8 Flash**     | 低レイテンシを活かした試行錯誤、手数の多いコード生成。                                            |
| **局所的な構文エラー・リファクタリング** | **Gemini 3.8 Flash**     | 開発テンポを落とさず高速に消化するタスク群。                                                      |

### 1.2 実務的な切り替え運用ルール
1. **通常の実装は Flash で回す**: 基本的なコーディング、ウィジェット追加、スタイル微調整。
2. **「2往復ルール」で Pro / Argon へスイッチ**: Flash に修正を指示して2往復してもコンパイルエラーが通らない（別の借用エラーを生む）場合は、即座に Pro / Argon に切り替え、`cargo check` のログを丸ごと渡して根本設計から見直させる。
3. **骨格が通ったら Flash に戻す**: アーキテクチャの芯が通った段階で再び Flash に戻し、実装スピードを最大化する。

## 2. GUI基盤の役割分担：eframe と egui の違い

### 2.1 役割の明確な分離

* **egui (GUIライブラリ)**:
  * 純粋なUIロジック、レイアウト計算、入力イベント判定、描画メッシュ生成を担当。
  * OSへの依存を持たず、これ単体ではウィンドウを表示できない（純粋な描画命令生成器）。
* **eframe (egui framework / 公式フレームワーク)**:
  * OSウィンドウの管理（winit等）、GPU描画バックエンドの初期化（wgpu / OpenGL）、OS入力イベントの抽象化。
  * `eframe::App` トレイトを提供し、`update` 関数を毎フレーム呼び出すイベントループ基盤。

### 2.2 構造関係図

```text
+-------------------------------------------------------------------+
| OS (Windows / macOS / Linux / WebAssembly)                        |
+-------------------------------------------------------------------+
                                ▲
                                │ ウィンドウ管理 / 入力 / GPU (DirectX 12 / Metal / Vulkan)
+-------------------------------▼-----------------------------------+
| eframe (NativeOptions, run_native, イベントループ, wgpu)          |
+-------------------------------------------------------------------+
                                │ 毎フレームのコンテキスト提供 (ctx)
+-------------------------------▼-----------------------------------+
| egui (CentralPanel, SidePanel, Layout, Painter, Visuals, 状態判定)|
+-------------------------------------------------------------------+
                                ▲
                                │ 呼び出し
+-------------------------------▼-----------------------------------+
| vivivi 共通層 (vivivi-core / modes / vi / app共通ロジック)        |
+-------------------------------------------------------------------+
```

## 3. RustネイティブGUIフレームワークの比較検討

Webフロントエンド技術（React, HTML/CSS, Tauri等のWebView）を除外し、Rustネイティブで完結する有力なGUIフレームワークの選定比較：

| フレームワーク                | アーキテクチャ                                     | 描画性能・レイテンシ                             | デザイン自由度・ルック＆フィール                                            | 成熟度・エコシステム                 | vivivi への適合度                    |
| :---------------------------- | :------------------------------------------------- | :----------------------------------------------- | :-------------------------------------------------------------------------- | :----------------------------------- | :----------------------------------- |
| **egui / eframe**<br>*(採用)* | **即時モード (Immediate)**<br>(毎フレームUI再評価) | **極めて高速**<br>(軽量GPU直結 / wgpu)           | 単一のRustコードで完結。テーマ（Visuals）を上書きすることでモダン化が可能。 | **極めて高い**<br>(作例・知見が豊富) | **最適**<br>(TUIロジックと直結)      |
| **GPUI**<br>*(Zed基盤)*       | **リテインド＋GPU直結**<br>(React/Tailwind寄り)    | **最速・極限の低遅延**<br>(Metal/DirectX/Vulkan) | Tailwind CSS風のユーティリティ記法。汎用部品が乏しく自作前提。              | **低い**<br>(API変更多、知見少)      | **時期尚早**<br>(実装・設計コスト大) |

| **Iced**                      | **リテインド・リアクティブ**<br>(Elm Architecture) | **高速**<br>(wgpuベース)                         | Model-Update-Viewの強固な状態管理。コード量は増えるが堅牢。                 | **普通〜高**                         | **保留**<br>(キー即時性との相性)     |

## 4. なぜ Zed は GPUI を自作・採用したのか（非同期アーキテクチャの重要性）

Atom の開発者（Nathan Sobo ら）が立ち上げた Zed が、既存フレームワークを使わずに GPUI を開発した背景：

1. **Atom（Electron / Web技術）の限界の打破**:
   DOM、CSSエンジン、JavaScriptランタイムを挟む限り、タイピング遅延（Input Latency）をゼロにすることは構造上不可能であるという結論。
2. **ProMotion (120Hz) の完全追従**:
   1フレームあたり 8.33ms 以内に全描画を完了させるため、汎用GPU抽象化を排してプラットフォーム低レベルAPI（DirectX 12 / Metal / Vulkan）に直結させた。
3. **即時モードの省電力克服（ハイブリッド・リペイント）**:
   通常時は入力イベント駆動（Reactive Mode）で 0% CPU を維持し、スクロールやアニメーション発生時のみ GPU 連続描画（Continuous Mode）へ切り替える設計。
4. **マルチスレッド非同期アーキテクチャ**:
   Tree-sitter（構文解析）、LSP（Language Server）、非同期I/Oが走っても、UIスレッドが絶対に1フレームもブロックされない機構をフレームワークの核に据えた。

## 5. egui のデザイン改善と脱「野暮ったさ」の手法

egui が野暮ったく見える主因は「ゲーム開発・デバッグ用ツールのデフォルト設定」にある。全体テーマ（`Visuals`）を起動時に上書きすることで、洗練されたモダンエディタの外観が得られる。

### 5.1 代表的なモダンテーマの比較

| 項目                 | **Tokyo Night**                            | **Catppuccin (Mocha)**                         |
| :------------------- | :----------------------------------------- | :--------------------------------------------- |
| **ベーストーン**     | クール・深海のような青紫・ネイビー         | ウォーム・モカ／エスプレッソ調のダークグレー   |
| **アクセントカラー** | ネオンシアン、ライトブルー、マゼンタ       | ラベンダー、ミント、ピーチ、ローズウォーター   |
| **UIの印象**         | サイバー感、引き締まったシャープなテック感 | 柔らかく目に優しい、居心地の良い佇まい         |
| **向いている用途**   | ログビューア、ターミナル連携、モニタリング | テキストエディタ、ドキュメント閲覧、常駐ツール |

### 5.2 デザイン手戻りを最小化する 4 原則
1. **境界線（Stroke）を消す**: 標準の白枠で囲まれた四角いボタンをやめ、ホバー時の明淡差で表現する。
2. **角丸（Rounding）の付与**: ボタンやパネルに 4px〜6px の丸みを持たせる。
3. **背景の3段階コントラスト**:
   - ベース背景（一番暗いエディタ領域）
   - パネル／サイドバー（中間の暗さ）
   - 選択要素・アクティブ行（少し明るい）
4. **等幅フォントと線画アイコン（Phosphor Icons等）の活用**:
   テキストだけのボタンを避け、適度な余白（`item_spacing`）を確保する。

## 6. GUIフォント戦略：PlemolJP の標準採用と「半角1:全角2」の死守

TUI版は実行環境であるターミナル（Windows Terminal, Alacritty, WezTerm等）の設定フォントに委ねられますが、**GUI版（`vivivi-gui`）では公式標準フォントとして『PlemolJP』を採用** します。

### 6.1 PlemolJP を標準採用する決定打

1. **Zed と同じ美しさ（IBM Plex Mono 由来）**:
   Zed のエディタフォント（`Zed Mono`）のベースである **「IBM Plex Mono」** を欧文グリフに使用しているため、Zed と同等の洗練された知的かつモダンなコーディング体験が得られる。
2. **完全な「半角 1 : 全角 2」の等幅比率（East Asian Width）**:
   日本語グリフ「IBM Plex Sans JP」と精密に合成されており、全角文字の幅が半角文字の完全に2倍となるよう設計されている。
   - **罫線モード（Box Drawing）**: 縦横の交差点（`┌ ─ ┐ │ ┼`）が1pxもズレず直交する。
   - **CSVモード & Markdownテーブル**: カラム区切りが綺麗に垂直整列し、ガタつきを根絶できる。
3. **安全なライセンス（SIL Open Font License）**:
   商用・個人利用問わず自由に使用・再配布可能。

### 6.2 実用的なフォント読み込み・フォールバック階層設計

バイナリ肥大化を防ぎ、ポータブル性を両立させるためのロード順序：

```text
[第1優先: アプリ同階層フォント]
vivivi.exe と同一ディレクトリの `fonts/PlemolJP-*.ttf`
       │ (未配置の場合)
       ▼
[第2優先: システムインストール済みフォント]
OS登録済みフォント ("PlemolJP", "PlemolJP Console")
       │ (未インストールの場合)
       ▼
[第3優先: Windows標準高品位]
"BIZ UDゴシック" (MORISAWA) / "MS Gothic"
       │ (非Windows / 見つからない場合)
       ▼
[第4優先: システム標準]
OSデフォルト等幅フォント (Monospace / Courier)
```

## 7. プロジェクト構造：ヘッドレス状態層とマルチフロントエンド

### 7.1 クレート境界の再定義（最大の手戻り防止）

現在稼働中の `vivivi-app` は、TUI描画コードだけでなく、エディタの基幹状態（複数タブ管理、ウィンドウ分割木、バッファ管理、ファイルI/O、exコマンド実行、設定管理）を集約しています。
GUI版（`vivivi-gui`）を新設する際、これらのコア状態をゼロから再実装するのを防ぐため、**「共通アプリケーションコア（Headless App）」** と **「描画フロントエンド」** を明確に分離します。

```text
vivivi/
├── Cargo.toml               (ワークスペース定義)
├── crates/
│   ├── vivivi-core          (ヘッドレスな純粋バッファ・Undo・エンコーディング層)
│   ├── vivivi-vi            (Viモード状態機械・コマンドパーサー・キーバインド解析)
│   ├── vivivi-modes         (罫線、CSV、Migemo、アウトライン、差分、プロジェクト管理等の独自機能)
│   ├── vivivi-app           (エディタ基幹状態管理ライブラリ ＆ TUIフロントエンド)
│   │   ├── src/lib.rs       (App, Tab, WindowTreeNode, Exコマンド等の共通セッション層)
│   │   ├── src/main.rs      (TUI エントリポイント: vivivi.exe)
│   │   └── src/tui/         (Ratatui / Crossterm 専用描画・イベント層)
│   └── vivivi-gui           (Phase 5: egui / eframe 専用デスクトップGUIフロントエンド)
│       ├── src/main.rs      (GUI エントリポイント: vivivi-gui.exe)
│       └── src/gui/         (egui ウィジェット・Painter 描画層)
```

### 7.2 分離運用の原則と事前デカップリング要件
1. **TUI固有型の排除（事前リファクタリング必須）**:
   現在の `vivivi-app::tui::App` 構造体は、`ratatui::layout::Rect`（`window_rects` フィールド）および `crossterm::event::KeyEvent`（`recorded_macro_events` フィールド）に直接依存しており、`Cargo.toml` にもまだ `[lib]` ターゲットが存在しない。
   したがって Phase 5 着手時の **「ステップ 0」** として、これらをフロントエンド中立な独自型（`LogicalRect`, `AppKeyEvent`）へ抽象化し、`src/lib.rs` として公開するデカップリングを実施する。
2. **`App` 状態の共有とマルチカーソル拡張性**:
   タブ操作（`gt`）、ウィンドウ分割（`:split` / `:vsplit`）、exコマンド（`:w`, `:%s`）の実行ロジックはすべて共通層に置き、GUI側は状態の参照と描画のみを担当する。また、Phase 5 の「マルチカーソル編集」を見据え、カーソル描画層はプライマリカーソル（`cursor: TextCursor`）に加えセカンダリカーソル群（`extra_cursors: Vec<TextCursor>`）を反復描画できる設計とする。
3. **座標系（文字セル vs ピクセル）の吸収**:
   TUI は `u16` の文字セル単位でレイアウト・スクロールを行うが、GUI（egui）は `f32` のピクセル単位でスムーススクロールを行う。共通層は「論理行・論理列オフセット」を保持し、GUI側でフォントのグリフ幅・行高（`line_height`）を乗算してピクセル座標へ変換する。

### 8.1 サイドバー・ファイルエクスプローラー（Box/NAS安全設計）
* `egui::SidePanel::left("file_explorer")` で開閉トグル（`:tree` / `:Explore` / `Ctrl-e`）。
* **非同期オンデマンド遅延読込**: 展開されたノード直下のみをバックグラウンドスレッドで取得し、ネットワークドライブ（SMB）やクラウドストレージ（Box Drive等）の走査でも UI スレッドを 1 フレームも停止させない。

### 8.2 ミニマップ（Minimap）と巨大ファイル（1GB超）のビューポート仮想化
* `CentralPanel` の右端領域に配置し、現在のエディタ表示範囲（ビューポート矩形）を半透明ハイライト表示。クリック・ドラッグで瞬時にスクロール位置を同期。
* **ビューポート仮想化（Viewport Culling）とガードレール**:
  Phase 5 の「巨大ファイル（1GB超 / `memmap2`）対応」と両立させるため、エディタ本文もミニマップも **「現在画面に見えている可視行（数十〜数百行）のみ」** をトークナイズ＆メッシュ生成する $O(\text{可視行数})$ レンダリングを徹底する。ファイルサイズが閾値（例: 10MB）を超える場合は、ミニマップの全文走査や Tree-sitter / LSP の全量パースを自動的にスロットリング（サンプリング描画・部分解析へ降格）し、メモリ枯渇（OOM）とフレームドロップを完全に防止する。

### 8.3 削除文字落下アニメーション（2D物理演算 ＆ 省電力ハイブリッド描画）
* 文字削除コマンド（`x`, `dd`, `dw` 等）発生時、削除された文字のピクセル座標・グリフ・初期速度（ランダムな跳ね上がり）を持つパーティクル構造体を生成。
* `ui.painter().text()` でエディタ最前面にオーバーレイ描画し、重力加速度 $g$ に従って落下・フェードアウトさせる。
* **省電力ハイブリッド制御**: パーティクルが存在する間のみ `ctx.request_repaint()` で 60fps〜120fps のアニメーションループを駆動し、全パーティクルが消滅した瞬間に自動で入力待機（0% CPU）に戻す。

### 8.4 Tree-sitter ＆ LSP の GUI レンダリング
* **ハイライトの多層レイヤリング**: ファイルオープン直後の 0ms 目は内蔵トークナイザー（`vivivi-modes::syntax`）で即座に着色し、バックグラウンドで Tree-sitter の構文木解析および LSP の Semantic Tokens が完了し次第、順次高精度な色へ上書きする。
* **LSP 診断情報 (Diagnostics)**: エラー箇所の文字下部に赤・黄の波線（Squiggly underline）を描画し、ガターに警告アイコン（`E`/`W`）を表示。
* **ホバー ＆ 補完ポップアップ**: `egui::Area` を使用してカーソル直下に最前面フロートウィンドウをポップアップ表示。

### 8.5 日本語 IME インライン入力と Vi モード連携（カスタム描画の最重要要件）
egui 標準の `TextEdit` ウィジェットを使わずに `Painter` で独自描画する場合、そのままだと OS の日本語 IME が機能しない。以下の IME 統合プロトコルを必ず実装する：
1. **IME 座標通知**: `ViMode::Insert` またはコマンドライン入力中、毎フレームのカーソルピクセル座標から `ctx.output_mut(|o| o.ime = Some(egui::output::IMEOutput { rect, cursor_rect }))` を出力し、OS の変換候補ウィンドウをカーソル直下に追従させる。
2. **プリエディット（未確定文字列）のインライン描画**: `egui::Event::Key` だけでなく、確定文字列 `egui::Event::Text(String)` と変換中イベント `egui::Event::Ime(egui::ImeEvent::Preedit(String))` を捕捉し、未確定文字列をカーソル位置へ下線付きでインライン描画する。
3. **Normal モード復帰時の IME 自動リセット**: `Esc` キーで `ViMode::Normal` へ戻った瞬間、`o.ime = None` として IME 状態を解除し、ノーマルモードでの日本語誤入力（あいうえお暴発）を防止する。

### 8.6 バイナリモード（Hex Editor）＆ プロジェクト可視化グラフ（Visualize）
* **バイナリモード**: `CentralPanel` の描画モードを切り替えることで、「アドレスオフセット列」「16進ダンプ列（16バイト折返し）」「ASCII表示列」の3列同期グリッドを `Painter` で高速描画し、バイト単位のカーソル移動・直接編集を行う。
* **プロジェクト可視化グラフ**: インクルード依存関係・ファイルサイズ・更新鮮度をノードとエッジで表現する 2D 力学モデル（Force-Directed Graph）を `CentralPanel` 上に描画。ノード間の斥力（クーロン力）とエッジの引力（フックの法則）を計算し、系全体の運動エネルギーが閾値以下に収束した時点で `ctx.request_repaint()` を自動停止する省電力物理ループを採用する。

## 9. ViVi / openViVi の歴史と ViViVi の存在意義

### 9.1 作者・津田伸秀（つだ のぶひで）氏の足跡
* **Windows黎明期の金字塔**:
  Windows 95/NT 時代に Win32 API を直接叩くネイティブな Vi クローンとして ViVi を開発・公開。卓越した安定性と速度で絶大な支持を得た。
* **日本語（IME）と Vi の完全調和**:
  当時の海外製エディタが太刀打ちできなかった「日本語インライン入力」と「Viのモード遷移」のシームレスな統合を実現。
* **Qtへの移植とオープンソース化**:
  クロスプラットフォーム対応を目指し、膨大な C++ コードをご自身で Qt に移植して **openViVi** として公開。

### 9.2 Zed が存在しても「ViViVi」が必要な理由
Zed は「フルスペックのコード開発環境（IDE）」であり、重機の立ち位置にある。対して ViViVi は「超軽量で独自の切れ味を持つ職人ツール」として確固たる住み分けが存在する。

1. **罫線モード（Box Drawing）**:
   カーソルを矢印で動かした軌跡に自動で罫線（`┌ ─ ┐ │ └ ┘ ┼`）を引き、交差点を自動判定する。メモ書きや仕様書のテキスト図解を 0 秒で作成可能。
2. **CSV モード（カラム整形・編集）**:
   表計算ソフトを起動せずとも、縦列を整列表示し、Vi のキー操作でカラム間を自在に飛び回って編集・ソート・抽出を行う。
3. **TUI と GUI のハイブリッド**:
   SSH接続先やターミナル内では `vivivi`（TUI）、デスクトップでは `vivivi-gui` という、同一の操作体系とコアロジックを環境に応じて使い分けられる。

### ステップ 5: パフォーマンス最適化とイミディエイトモードの落とし穴【Phase 5 実装知見】

> [!IMPORTANT]
> egui は本来ミリ秒未満・超軽量で動作するフレームワークですが、イミディエイトモード特有の性質と Rust の Debug プロファイル仕様により、以下の対策を講じないと「高CPU負荷」「動作のカクつき」が発生します。

| ボトルネック要因                           | 発生していた現象                         | 実施した恒久対策                                                                                    |
| :----------------------------------------- | :--------------------------------------- | :-------------------------------------------------------------------------------------------------- |
| **Cargo Debug プロファイルの非最適化**     | `cargo run` 時に描画が激重・CPU高負荷    | ルート `Cargo.toml` に `[profile.dev.package."*"] opt-level = 3` を追加し、GUI描画クレートをフル最適化。  |
| **毎フレーム全可視行の構文解析**           | 入力やカーソル移動時にCPUが跳ね上がる    | 行ハッシュキーによる `syntax_cache` を導入し、テキスト変更のない行の Lexer パースを O(1) スキップ。    |
| **描画ループ内での毎行ヒープ割り当て**     | 文字列や真偽値ベクタの malloc/free 多発  | ループ外にスクラッチバッファ（`chars_buf`, `search_matched_buf` 等）を配置し、毎フレームゼロアロケート化。|
| **全角文字描画時の String 生成**           | 日本語文字の描画時にメモリ確保が発生     | `ch.to_string()` を `ch.encode_utf8(&mut [0u8; 4])` に置換し、スタックメモリでゼロアロケーション描画。    |
| **Windowsシステムフォントの大量一括ロード**| 起動時間遅延とグリフ線形探索の負荷増大   | PlemolJP を優先し、存在しない場合のみ順次1つだけフォールバックするスマートローディングへ刷新。    |

```
